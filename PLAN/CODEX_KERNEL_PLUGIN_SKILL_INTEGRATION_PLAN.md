# Codex Kernel Plugin Skill Integration Plan

Last updated: 2026-06-25

## Total Goal

Make AstraBridge resilient to official Codex CLI/kernel upgrades and expose official Codex plugin/skill ecosystem capabilities through AstraBridge's own product UI.

This plan has two linked goals:

- build a compatibility layer so an agent can semi-automatically upgrade and validate the official Codex CLI/kernel without relying on guesswork
- integrate official plugin and skill discovery, status, installation, update, icon, and project/automation enablement surfaces into AstraBridge

The target is not one-click unattended kernel upgrades. The target is a documented, probe-driven, evidence-preserving workflow where a future agent can:

- identify the currently used Codex CLI binary, version, app-server behavior, MCP behavior, plugin behavior, and skill behavior
- compare the detected kernel against AstraBridge's verified compatibility matrix
- run a fixed kernel upgrade smoke suite before marking a new kernel as verified
- discover official/local plugins and skills without writing secrets or official Codex state
- let users manage plugin/skill availability from AstraBridge UI instead of editing raw files
- attach plugin/skill presets to projects, capability runtime, and automations in a controlled way

Initial integration target:

- current local baseline: `codex-cli 0.137.0`
- known local binary path as of plan creation: `D:\Tools\OpenAI\Codex\bin\codex.EXE`
- official release anchor: Codex CLI `0.137.0` / `rust-v0.137.0`, released 2026-06-04
- first plugin/skill target line: official plugin and skill surfaces available in the 2026-06-04 / `0.137.0` line and compatible later kernels

If the user later clarifies that "6.4" means a different official product version or catalog cut, the executing agent must record that interpretation in this plan before implementing steps that depend on it.

## Notes And Constraints

- Do not store API keys, bearer tokens, cookies, authorization headers, refresh tokens, official account credentials, or provider raw secrets in git, UI state, logs, reports, plugin metadata, skill metadata, or smoke artifacts.
- Do not read Desktop key files or other plaintext secret sources unless the user explicitly authorizes that exact action for the current task.
- Do not write official Codex `~/.codex/config.toml`, official app state, or project `.codex*` files during normal AstraBridge operation.
- Keep `.abproj` and workspace-local `.astrabridge/` as the only normal product project state paths.
- Keep AstraBridge's isolated `CODEX_HOME` and optional WSL Codex home as the only normal Codex state roots used by the product.
- Do not call or depend on private official Codex App APIs. Prefer public CLI commands, stable app-server protocol behavior, local manifests, and documented MCP/plugin/skill surfaces.
- Preserve diagnostics, validation reports, raw command metadata, and smoke evidence by default under `PRIVATE/**` or workspace-local validation paths, with secrets redacted before durable storage.
- Do not auto-enable newly discovered plugins or skills globally. Prefer explicit project-level or automation-level enablement.
- Official icons may be used only when licensing and provenance are clear. Otherwise create AstraBridge-rendered replacement icons and label their provenance clearly in metadata.
- Plugin and skill installation/update must be reversible or at least auditable: record source, version, checksum when available, install root, and previous state snapshot.
- Follow the existing desktop design style: dense operational UI, predictable controls, no marketing hero layout, no nested cards.
- Each future execution round should complete exactly one numbered step from this plan, update the progress block, append a completion record, and stop.

## Current Surface Summary

As of 2026-06-25:

- AstraBridge currently detects and launches an external Codex CLI/app-server runtime.
- The current local Codex CLI version has been observed as `codex-cli 0.137.0`.
- The repo contains a hard-coded model catalog baseline `CODEX_CLI_BASELINE = "0.137.0"`.
- Runtime status already exposes a `codex_cli` path and isolated `CODEX_HOME`.
- WSL support has a separate AstraBridge-managed Codex install/bootstrap path.
- MCP preset management exists, including `astrabridge_capabilities`.
- Capability and automation UI surfaces now exist, but plugin/skill management is not a first-class product area.
- There is no explicit Codex kernel compatibility matrix, kernel probe report, upgrade smoke suite, plugin inventory, skill inventory, icon provenance model, or project-level plugin/skill preset UI.
